## 0. 结论前置

**一句话**：**"接受率升高"在 G2/G3 里默认应判为可疑信号（suspicious），而非收益信号**；但它**不能单独定案**——必须用"三角互洽 + 深位条件率形状 + 边界巧合"三件套合判，最终由 C9（贪心序列逐位相等）一锤定音。

**判别量清单（≥3 条，全部可只用 Prometheus 计数器算出）**：

| # | 判别量 | 诚实截短的预期 | 回顾性接纳（作弊）的表现 | 强度 |
|---|---|---|---|---|
| **D1** | **三角互洽**：`completion_tokens ≟ num_accepted + num_drafts` | 恒等成立（±EOS/max_tokens 截尾） | **破**：accepted 虚增而 completion 未增 | 硬（抓计数器造假） |
| **D2** | **接受长度自洽**：`reported_accept_len ≟ completion_tokens/num_drafts − 1` | 恒等成立 | **破**：accept_len 升但 drafts 未按比例降 | 硬（纯计数器，几乎无噪声） |
| **D3** | **深位条件接受率形状**：`r_i = A_i / O_i`（per-position 计数器） | 单调递减，剪后**不越界**（r_i 不得 > r_{i-1}） | **破**：某深位 r_i 上升/持平且 O_i 塌缩，且异常位置恰好 ≈ median(l_r) | 中强（形状+边界巧合） |
| **D4** | **深位 offered/accepted 比值**：`ρ_i = O_i / A_i` | 深位 ρ_i **升或持平**（offer 少、accept 更少） | **破**：深位 ρ_i 骤降（offer 少但 accept 相对变多） | 中 |
| **D5** | **绝对接受量守恒**：gate-on 的 `num_accepted` vs gate-off | ≤（offer 变少，接受不可能变多） | **破**：accepted_on > accepted_off 而 output 体量持平 | 中（需同载荷对拍） |

**现场判定规则（一行，可抄进 G2 验收单）**：

> **若 `accept_len(gate-on)` 较 gate-off 升幅 > 5%（且超出 3 波极差）而 `completion_tokens/num_drafts − 1` 与之不自洽，或任一深位 `r_{i+1}/r_i > 0.70`（越过本负载期望带上限，见 §0.5）且该位 `O_i` 相对塌缩 → 判 FAIL，回查 C10（并优先复核 C2/C6 是否把当前步置信/实现值泄漏进了截短边界）。**

**最小样本量建议**：每个**待判位置的 `O_i` ≥ 2000**（约 2000 个 verify 步），且 **≥3 波独立重复、符号一致**；低并发（max-num-seqs=12）下**不得用单波均值定案**——用 3 波中位 + 波间极差做噪声带。详见 §4。

**判据分层（team-lead 指定，用于安排 G2 采样计划）**：

| 层 | 判据 | 能否脱离 G2 先验 | 依赖 | 成本 |
|---|---|---|---|---|
| **L1 先验层** | **D1、D2** | ✅ **是**——恒等式级，**只需 HTTP usage + 两个 spec 计数器**；单请求、gate-on 单臂即可自验 | 无（不依赖 gate-off、不依赖样本量、不依赖负载） | 零（2 条断言） |
| **L1 先验层** | **D3 的期望形状基线** | ✅ 是——用**历史 gate-off 数据**（六门/来源②）即可标定 | 无（离线） | 零 |
| **L2 对拍层** | **D5** | ❌ 否——**必须等两臂跑起来** | gate-on vs gate-off 同载荷冷口径 | 1 个 A/B 窗 |

## 1. Q1：回顾性接纳在我们这套实现下"长什么样"（可构造的错误实现）

### 1.1 机理：作弊的共性 = 准入决策看了"被准入对象的实现值"

non-anticipating（NA-2）的红线是：**接纳/验证第 k 个 token 的决定，绝不能依赖 x_k 的实现值**。回顾性接纳（retrospective admission）就是踩这条线的一类实现，其统一形态是：

```
决策所用信息  ⊇  被决策对象的实现值
```

在我们这套"置信头 + 调度侧截短"的架构里，**最危险的是它伪装成"自适应验证"的天真实现**——因为"只验证有把握的前缀"这句话，天真写法就是去偷看目标模型的 logits。下面给三个伪代码级样本（α/β 是最可能被无意写出且最难察觉的；γ 是纯指标造假）。

### 1.2 Cheat-α：非前缀回溯接纳（跳过前缀语义，"任意深位命中就拉长"）

```python
# 诚实实现（对照）：
#   accepted = rejection_sampler(target_logits, draft_tokens)   # 连续前缀
#   a = count_consecutive_true(accepted)                         # a ≤ k
#   emit(draft_tokens[:a]); emit(bonus_token(target_logits[a]))

# —— 作弊实现 α ——
accepted_mask = rejection_sampler(target_logits, draft_tokens)   # 前缀掩码
a_honest = count_consecutive_true(accepted_mask)
a = a_honest
for i in range(k - 1, a_honest, -1):        # ← 作弊起点：向深处回看
    if argmax(target_logits[i]) == draft_tokens[i]:   # 只要某深位"恰好"被目标模型认可
        a = i + 1                            # 就把接纳前缀回溯性拉长
        break
emit(draft_tokens[:a])                       # 提交了本应被拒的中间槽
```

**为何虚高接受率**：`a` 的增大依赖 x_i 的实现值（`argmax(target_logits[i]) == draft_tokens[i]` 是"事后"才可知的）。它把"深位偶然命中"错当成"前缀被接受"，**同时违反前缀语义与 NA-2**。论文式(10) 的分布污染（Pr(A)=0.85≠0.7）正是这一类。

### 1.3 Cheat-β：选择性验证（先看真实结果，再决定验几个）★ 最危险

```python
# —— 作弊实现 β：把"截短"接到目标前向之后 ——
logits = target_forward(all_k_draft_tokens)          # 先算真实目标分布
would_accept = rejection_sampler(logits, draft_tokens)
l_r = count_consecutive_true(would_accept)           # ← 用未来信息定"截短长度"
schedule_only_first(l_r)                             # 假装成"按置信截短"
# 幻觉点：作者会以为这是"只验证会被接受的部分，省算力"
```

**为何最危险**：它**长得像**"自适应验证"的合理优化，且在指标上表现完美（verify token 数↓、接受率↑、无正确性报错）——但它就是论文反例的"回顾性全局搜索"：`l_r` 依赖 draft token 的实现值 → NA-2 违反 → **silently breaks losslessness**（论文原话）。
**与我们实现的区别（关键）**：我们的 `l_r` 来自 **stale 一步的置信快照**（`get_stale_confidences` 取 `_conf_step−1`），**在任何目标前向之前就已固定**；β 的 `l_r` 来自**本步目标前向之后**。这个"先后顺序"是唯一的、也是决定性的区别——**这正是 C1/C2 静态检查要钉死的东西**。

### 1.4 Cheat-γ：计数器层面造假（真算数不 cheat，但指标 cheat）

```python
# —— 作弊实现 γ：分母动手脚 ——
num_draft_tokens_total -= num_trunc      # 截短时把"没验证的"也从分母剔除
# 或：per-position 计数器在截短边界之外仍递增（把"未 offered"计入 A_i）
# 或：把 bonus token 也算进 accepted_tokens（口径漂移 +1/k）
```

**为何要单列**：前两种靠"算法违规"抬高分子，γ 靠"**记账口径**"抬高比值。**γ 是唯一能被 §2 的 D1/D2 纯计数器直接抓住的**（三角破、自洽破），而 α/β 必须靠 D3/D4/边界巧合 + C9。

## 2. Q2：如何从数据上区分「真收益」与「回顾性接纳虚高」

### 2.0 先破一个直觉：**不能只看 `accepted/drafts` 比值**

**[代数]** 我们先把恒等式钉死（用六门实测数据核验，见 §2.1）：

```
num_accepted / num_drafts  =  mean acceptance length（不含 bonus）        …… (1)
num_accepted + num_drafts  =  completion_tokens（投机每步 = a + 1 bonus）  …… (2)
```

**(1) 的推广（前缀语义的线性期望）**：设 `m_i = A_i / D`（位置 i 的**边际**接受率，`D`=num_drafts，`A_i`=位置 i 接受计数），则
```
mean accepted length = Σ_i m_i        …… (3)   [实锤：平凡恒等，Σ 指示变量期望]
```
**[本地实据]** 用六门实测：A=[2453,1290,680,378,239,151], D=3806 → Σ m_i = 1.3639 ≈ 报告 1.364 ✓；含 bonus = 2.364 ✓；ΣA_i = 5191 = accepted_total ✓。
→ **这意味着：`accepted/drafts` 比值本身是"分子/分母"两人份的量，作弊只要动任一侧就会变，但不告诉你动的是哪侧。** 必须拆开看分子与分母各自的走势。

### 2.1 D1 — 三角互洽（硬，抓 γ 型/记账型）

**恒等式**：`completion_tokens ≟ num_accepted_tokens_total + num_drafts_total`（±1 个末步无 bonus、±prefill 不计入）。
**用法**：两臂各自验一次；再看**差分**：`Δcompletion ≟ Δaccepted + Δdrafts`。
- **诚实**：三者自洽（输出体量固定 → Δcompletion≈0 → Δaccepted ≈ −Δdrafts，**符号相反且量级相当**）。
- **作弊（γ/虚增）**：`Δaccepted > 0` 而 `Δcompletion ≈ 0` 且 `Δdrafts` 未同步负 → **破**。

**[本地实据]** 六门 run：5191 + 3806 = 8997 = 该 run 应有 completion 总量（`(accepted+drafts)/drafts=2.364` 同源校验）。**建议**：G2 直接把它写成断言，成本为零。

### 2.2 D2 — 接受长度自洽（硬，纯计数器，噪声≈0）

**[代数]** 由 (1)(2)：`accept_len_excl_bonus ≡ completion_tokens / num_drafts − 1`。
**这是同一枚硬币的两面**：给定输出体量，**accept_len ↑ 必然要求 drafts ↓**，二者不能各自独立。
- **诚实**：报表里的 `accept_len` 与 `completion_tokens/drafts − 1` 一致到浮点级。
- **作弊**：报了 `accept_len` 上涨，但 `drafts` 没按比例降（因为接受数是虚增的，没真换来"每步多推进"）→ **两者对不上**。

**这条的威力**：它不依赖任何阈值、不依赖样本量、不依赖负载——**只要系统同时暴露 completion_tokens（HTTP usage）与两个 spec 计数器，就能零成本判**。**[本地实据]** 六门数据自洽（1.364 = 5191/3806）✓。

### 2.3 D3 — 深位条件接受率形状 + 边界巧合（中强，作弊的主判别）

定义三套位置量（**per-position 计数器已实测存在**：`vllm:spec_decode_num_accepted_tokens_per_pos_total{position="0".."k-1"}`，drafts 总量可得）：

| 量 | 定义 | 含义 |
|---|---|---|
| `O_i` | 位置 i 被 **offered**（调度进 verify）的次数 | 截短会**直接压低深位 O_i** |
| `A_i` | 位置 i 被接受的次数 | 由 per-pos 计数器直接读 |
| `r_i = A_i / O_i` | **条件**接受率（在"被 offered"前提下） | **唯一携带位置形状信息的量** |
| `m_i = A_i / D` | 边际接受率 | ① 的分解项 |

**诚实的预期形状**：`r_i` 随 i **单调递减**（越深越难）；剪短只改变 **O_i 的分布**（深位被 offered 变少），但**不改变 r_i 的递降趋势**——因为截短依据的是 **stale 置信**，与被 offered 的 token 的实现值无关。
**作弊的特征形状**：
1. **破坏单调**：出现 `r_i > r_{i-1}`（哪怕只 10%）；
2. **边界巧合**：异常抬升的位置 ≈ `median(l_r)`（即被 offered 的深位正好是"注定被接受"的那批）；
3. **分子不动分母塌缩**：`O_i →`小 而 `A_i` 不按比例小 → `r_i` 被选择偏差抬起。

**机理（对应 Q3）见 §3。**

### 2.4 D4 — 深位 `ρ_i = O_i / A_i`（中）

`ρ_i` 与 `r_i` 互为倒数，但作为"比值"对分母波动更稳，适合现场读数。
- **诚实**：深位 `ρ_i` **升或持平**（offer 减少、accept 减少得更多 → 比值升）。
- **作弊**：深位 `ρ_i` **骤降**（offer 少了，但 accept 相对多了）。

### 2.5 D5 — 绝对接受量守恒（中，需同载荷对拍）

**诚实的下界论证 [推断，强度中高]**：截短只减少 offered，**不可能凭空造出 gate-off 中不存在的接受**；在贪心下更应**逐位相同**。故 `num_accepted(gate-on) ≤ num_accepted(gate-off)`（同载荷、同 max_tokens、输出体量持平）。
- **作弊**：`accepted_on > accepted_off` 而 completion 持平 → 出现了 gate-off 里不存在的接受 → **直接指向 α/β**。
- **⚠️ 注意**：这是"绝对量"判据，**必须同载荷冷口径**（09-09 踩过前缀缓存伪通过）；且低并发下 output 体量本身有抖动，需 D2 自洽先兜底。

### 2.6 关于"verify/accepted 比值"的诚实纠正 [代数]

task 提示"verify token 数与 accepted token 数的比值在作弊下会失真"。**实算后必须纠正**：
```
R = num_draft_tokens_total / num_accepted_tokens_total
  = (D·k) / (D·accept_len) = k / accept_len            …… (4)
```
**[代数]** R **代数冗余**于接受长度（k 固定时 R ≡ k/accept_len）。**[本地实据]** 22836/5191 = 4.399 ≈ 6/1.3639 = 4.399 ✓。
→ **总量层面的 verify/accepted 比值不提供任何独立于 accept_len 的信息**；G2 验收单不应把它列为独立判别量。**真正有意义的是 per-position 的 `ρ_i = O_i/A_i`**（携带"剪了哪些位置"的信息）——即 D3/D4。这是与提示方向的一处独立修正，实测可复核。

## 3. Q3：per-position 接受率的预期形状，与"位置 3 反升"的机理

### 3.1 预期形状：单调递减（实测锚点）

**[本地实据]** 两个来源（负载不同，不可跨源直比）：
- 来源①（短答案+中文推理，k=6）：`r = 0.64 / 0.34 / 0.18 / 0.10 / 0.06 / 0.04`
- 来源②（W2 热态 vision）：`r = 0.86-0.92 / 0.71-0.77 / 0.52-0.70 / 0.32-0.39 / 0.22-0.26 / 0.07-0.13`
- bench 负载深位 `p5 ≈ 0.23`

**统一形态**：**严格单调递减**，且递减率本身随深度加大（末端近似几何衰减）。这是"越深越难预测"的必然结果，与置信头的校准无关。

### 3.2 "剪短后位置 3 的接受率反而升高或持平"→ 说明什么

**分两种情形，必须靠 D1/D2/D5 与边界巧合来分离：**

**情形 A（可解释的良性抬升，不判 FAIL）——只可能"小幅、且不破坏单调"**
诚实剪短后，被 offered 的深位是**高置信前缀**的延伸；因置信与接受正相关，**条件**接受率 `r_i` 可以**小幅上抬**（条件在"高置信"上的选择效应）。
**但铁律**：`r_3 ≤ r_2` **不得被越过**，且 `O_3` 必塌缩、`A_3` 不增。若满足 → 良性，放行。

**情形 B（回顾性接纳，判 FAIL）——"越界抬升"或"分子不动分母塌缩"**
机理链：
1. 截短边界 `l_r` 若用了**当前步的置信/实现信息**（C2 违规），或 verify 后才按真实结果回头剪（Cheat-β），则"能留到位置 3 被 offered"这件事**不再与 outcome 独立**；
2. 结果是 `{位置 3 被 offered 的样本}` = `{注定被接受的样本}` ⊂ 全体；
3. 于是 `r_3 = A_3/O_3` 被**选择偏差**抬起，甚至 `r_3 > r_2`；
4. 同时 `O_3` 大幅塌缩（因为只有"注定成功"的才留下）——**这正是 D3 的"边界巧合 + 单调破坏"，是作弊的指纹**。

**可观测推论**：情形 B 下，异常抬升的位置会**随 CONF_MIN 增大而向浅位移动**（边界 `median(l_r)` 变小）——**做一次 CONF_MIN 扫描即可定位"抬升位置"是否跟着边界跑**；这是极强的一次性判别（见 §5 判定规则旁注）。

**量化版（用 §0.5 的比值带替代"单调"弱断言）**：判 FAIL 的充分条件可写成
```
r_{i+1}/r_i > 0.70  且  O_{i+1} 相对塌缩  且  该异常位置随 CONF_MIN 增大向浅位漂移
```
三者同现 → 回顾性接纳，铁证（单条越界不足，须三者合判，以避开良性抬升的误判）。

**一句话**：**位置 3 接受率"反升"本身不是罪证，但"反升且越界（`r_{i+1}/r_i > 0.70`）且 O_i 塌缩且抬升位置随阈值漂移"是**。

## 4. 低并发（max-num-seqs=12）噪声掩蔽与最小样本量

### 4.1 为什么低并发最危险

- **深位样本被截短反向惩罚**：要看 `r_3`，只有 `l_r ≥ 4` 的步才 offer 到位置 3。CONF_MIN 越大，`O_3` 越小 → **噪声最大的地方恰是我们要看的地方**（D3 的可检性被 CONF_MIN 直接侵蚀）。
- **低并发 → 单位时间步数少**：12 路并发下攒够深位计数更慢。
- **计数型噪声**：`A_i` 近似二项/Poisson；深位 `r_i` 小（0.04~0.10），**相对噪声 = 1/√(O_i·r_i) 会很大**。

### 4.2 最小样本量（按 D3 的可检性反推）

**双边检验、α=0.05、power=80%**，检测深位条件率**相对变化 δ**（`r` 基准 0.10）：

```
n ≈ (z_{α/2} + z_β)² · r(1−r) / (δ·r)²
  = (1.96 + 0.84)² · 0.09 / (δ·0.10)²
```

| δ（相对变化） | 需要 `O_i`（该位 offered 次数） | 备注 |
|---|---|---|
| 50% | ≈ 280 | 只抓"大作弊"，不够 |
| 30% | ≈ 780 | D3 最低门槛 |
| **20%** | **≈ 1760** | **建议默认** |
| 10% | ≈ 7000 | 低并发不现实 |

**建议（写进 G2/G3 验收单）**：
1. **每个待判位置 `O_i ≥ 2000`**（对应能检出 ≥20% 的相对抬升）。深位若达不到，则该位的 D3 **降级为参考**，不得据此单独定案。
2. **≥3 波独立重复，取中位，并要求符号一致**（3 波同号才算信号；否则视为噪声）。
3. **噪声带 = 3 波极差**（沿用既有基线纪律：如 PR2048_C1 prefill 极差 ±1.1%、冷热带中位 3.2%）——**任何"抬升"必须超出本臂 3 波极差才计**。
4. **D1/D2 不受样本量限制**（恒等式，常数级置信）→ **低并发下应把 D1/D2 作为主力，D3/D4 作为佐证**。
5. 若必须判深位形状且 `O_i` 不够：**加大 prompt 长度/输出长度**（深位才显现，参考 g2-preflight §3.3 建议 512 token 中长输出、prose 深位衰减快），而不是无限拉长窗口。

**[推断，强度中]** 上述 n 为二项近似；实际 per-position 计数在请求内**不独立**（同一请求的位置强相关）→ 有效样本量小于计数总和，**建议把 `O_i ≥ 2000` 再乘 1.5~2 倍安全系数**（即 ≈3000~4000），或直接用"跨请求 bootstrap"估置信区间。

## 5.5 A. per-position 计数器 position 语义核对（开臂硬前置）

**为什么必须先做**：D3/D4 全部建立在"`position=i` = 第 i **槽位**"这一语义上。若实际语义是"第 i 个被**接受**的 token"（或 0-based/1-based 偏移），则 `r_i = A_i/O_i` 的分母无意义，D3 整条作废。

### 核对方法（4 步，用一条已知输出请求，无需改代码）

**准备**：gate-off（CONF_MIN=0，全 k 验证）、`temperature=0`、**单请求**、prompt 选择**深位会衰减**的长输出（建议 prose，512 token）；记录该请求的**完整输出 token 序列**（HTTP response）。

| 步 | 动作 | 判据 |
|---|---|---|
| **S1** | 发请求前记 metrics 快照 `m0`；请求结束后记 `m1`；取差分 `Δdrafts, Δdraft_tokens, Δaccepted, ΔA_i (i=0..k-1)` | `Δdraft_tokens == Δdrafts × k`（**这一步先确认槽位数=k 的满额语义**） |
| **S2** | **槽位语义自检**：因是单请求逐步生成，`Δdrafts` = 该请求的 verify 步数；断言 `Δdrafts ≥ 1` 且 `Δdraft_tokens = Δdrafts×k` | 若 `Δdraft_tokens` **不整除 k**，说明计数器按"实际 offered 槽"而非"满额 k"计数 → **记为 offered 语义（对 D3 仍可用，但 O_i 需另算）** |
| **S3** | **position 语义判别（核心）**：检查 `ΔA_i` 的**上界单调性**。因验证是**连续前缀**——若位置 i 被接受，则位置 0..i−1 必被接受——故**诚实的槽位语义必然满足 `ΔA_0 ≥ ΔA_1 ≥ … ≥ ΔA_{k-1}`** | **`ΔA_i` 单调不增 → 槽位语义成立（D3 可用）**；若 `ΔA_i` 出现**非单调**（如 A_3 > A_2），则语义**不是**槽位，需重定义 |
| **S4** | **独立交叉验证**：用该请求的**已知输出文本**与 `Δaccepted` 对齐——`Δaccepted + Δbonus == 该请求 completion_tokens`，且 `Δaccepted` 应 ≈ 该请求中"由 draft 直接贡献"的 token 数（可用同一 prompt 跑 gate-off 全 k 与 k=0 对照近似） | 闭合 → 语义确认；不闭合 → 回到 S3 重判 |

**判定依据（一句话）**：**"`ΔA_i` 单调不增"是槽位语义的必要且近乎充分条件**——因为前缀语义保证"位置 i 被接受 ⇒ 位置 i−1 被接受"，这是**与实现无关的物理约束**（论文 §2 前缀语义）。任何**破坏该单调**的 `ΔA_i` 都说明计数器不是按槽位计的。

**若判定为"非槽位语义"**：D3/D4 需改用 **offered-count 重算**（从 `l_r` 帧日志直接统计各位置被 offered 的次数作为 `O_i`，而非从 draft_tokens 反推），其余步骤不变。**[推断，强度中]** 该分支概率不高（六门 Σ=5191 自洽且形状单调递减，符合槽位语义），但**必须在开臂前用 S3 钉死**。

## 5.6 B. D1 边界项：同 run 采集口径与允差

### B.1 必须同时抓的计数器（同 run、同 engine label 口径）

**一次请求/一个窗口内，从同一时刻的 `/metrics` 抓取以下全部**（避免跨 run 拼接）：

| 源 | 字段 | 用途 |
|---|---|---|
| HTTP response | `usage.completion_tokens`（逐请求，**求和**） | D1/D2 的 `completion_tokens` |
| Prometheus | `vllm:spec_decode_num_accepted_tokens_total` | D1 的 `num_accepted` |
| Prometheus | `vllm:spec_decode_num_drafts_total` | D1/D2 的 `num_drafts` |
| Prometheus | `vllm:spec_decode_num_draft_tokens_total` | 交叉校验 `= drafts×k` |
| Prometheus | `vllm:spec_decode_num_accepted_tokens_per_pos_total{position="i"}` | D3/D4 |

**配对纪律**：**同一 `model_name` + `engine` label**；**同一窗口的前后快照差分**（`Δ` 而非累计值）；**冷口径**（uuid 冷算，避免缓存命中使 prefill 步不计入 spec 计入分母）。

### B.2 允差（D1 的边界项）

`num_accepted + num_drafts == completion_tokens` 的**边界偏差来源**：
1. **末步无 bonus**：生成在 max_tokens/EOS 处截断时，最后一步只 emit a 个（无 bonus）→ **每请求 −1**；
2. **EOS 提前终止**：最后一步的 bonus 可能是 EOS，不计入 completion → 仍在 −1 内；
3. **非 spec 步**：prefill 或 spec 被禁用的步 emit 1 token 但不计 drafts → 使 `completion_tokens > accepted+drafts`，**每请求 +（非 spec 步数）**，正常单请求长输出下 **≈ +1（仅首 token 或极少数）**；
4. **per-request vs 计数器聚合口径**：`completion_tokens` 是逐请求求和，spec 计数器是全局累计，**同 run 内应严格配对**。

**允差建议 [推断，强度中]**：

| 判据 | 严格式 | 允差 | 说明 |
|---|---|---|---|
| **D1（聚合，N 请求）** | `\|completion − (accepted+drafts)\| ≤ N` | **±1 per request** | 端点项（末步 bonus / 首 token）**每请求最多 1**；N 个请求故 ±N |
| **D1（单请求核对，S3/S4 用）** | `= accepted+drafts` 或 `+1` | **严格，或 +1** | 单请求下应严格等于或仅差 1（首 token / 末 bonus） |
| **D2** | `accept_len ≟ completion/drafts − 1` | **相对误差 ≤ 1/drafts** | 因 accept_len 本身 = accepted/drafts，D2 与 D1 同源；单请求下 `drafts` 小（几十~几百）→ 用 `1/drafts` 作容差 |

**结论**：**D1 单请求用"严格相等或 +1"；聚合用 ±1 per request。若偏差超过 ±1 per request（例如 ±3/请求），说明记账真有问题（非端点效应），判 FAIL。**
